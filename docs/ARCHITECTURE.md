# MedSBoX Pro — Architecture

## 1. Purpose

MedSBoX is a static-first web application backed by Firebase services. The architecture is designed to keep the public experience fast and simple while moving authorization, subscription state, protected downloads, and administrative operations behind trusted Firebase boundaries.

## 2. Runtime layers

```text
Browser
  |
  +-- Public UI (HTML/CSS/JS)
  |
  +-- Firebase Web SDK
  |      +-- Authentication (technical anonymous sessions where required)
  |      +-- Firestore (catalog + user/order state subject to Rules)
  |
  +-- Callable Cloud Functions
         +-- Orders
         +-- Activation codes
         +-- Redemption
         +-- Protected download tokens
         +-- Subscription expiry
```

### Public layer

Public HTML, CSS and JavaScript are treated as untrusted client code. No client-side value is considered authoritative for price, entitlement, role, or protected file access.

### Data layer

Firestore is the source of truth for live catalog, plans, offers, subscription state, orders and activation lifecycle. Firestore Rules enforce document-level authorization and validation.

### Trusted layer

Cloud Functions perform privileged operations that should not depend on browser integrity, including order creation, activation-code issuance/redemption, signed download URLs and subscription expiry processing.

## 3. Domain boundaries

| Domain | Primary collections / services | Owner |
|---|---|---|
| Catalog | `apps`, `offers`, `iosApps`, `iosPlans` | Firestore + Admin |
| Commercial plans | `plans` | Firestore + Admin |
| Customers | `users` | Auth + Firestore |
| Commerce | `orders` | Cloud Functions + Admin |
| Access | `activationCodes`, subscription fields on `users` | Cloud Functions + Rules |
| Protected downloads | `appDownloads`, `offerDownloads`, `iosDownloads`, Storage | Functions + Rules |
| Administration | `admins` | Firebase Auth + Firestore |
| Operations | `downloadLogs` and future audit collections | Functions |

## 4. Trust boundaries

1. Browser input is untrusted.
2. Firestore Rules are the authorization boundary for direct Firestore access.
3. Cloud Functions are the trusted boundary for privileged mutations and signed download generation.
4. Firebase Admin SDK is server-side only and must never be bundled into public assets.
5. Storage download paths are not treated as public URLs; protected files are served through short-lived signed URLs generated by trusted Functions.

## 5. Customer journey

```text
Discover
  -> Browse catalog
  -> Select plan
  -> Create/order reference
  -> Payment handoff
  -> Receive activation code
  -> Redeem code
  -> Subscription becomes active
  -> Access protected downloads
```

The public journey remains account-free from the user's perspective. Anonymous Firebase sessions are technical implementation details used only where identity is required by the security model.

## 6. Administrative journey

```text
Admin authentication
  -> Admin authorization
  -> Catalog / plans / orders / codes / users
  -> Firestore Rules + trusted Functions
  -> Auditability
```

Admin UI must never be considered the security mechanism by itself. Every privileged operation must be protected server-side.

## 7. Architectural rules

- Prefer small, reusable client modules over duplicated page logic.
- Keep business constants centralized and documented.
- Never trust prices, plan duration, role, subscription status, or download paths supplied by the browser.
- Prefer callable Functions for privileged workflows.
- Keep protected download metadata separate from public catalog documents.
- Use explicit document lifecycle states instead of ambiguous booleans when a domain needs more than two states.
- Validate data at both the trusted-function boundary and Firestore Rules boundary where direct writes are possible.
- Avoid introducing a dependency unless it materially improves reliability, security, performance, or maintainability.

## 8. Evolution path

The architecture is intentionally compatible with later additions such as a richer admin audit log, analytics, feature flags, additional platforms, automated payment verification, and more granular entitlement models without requiring a rewrite of the public catalog.
